# API du backend : routes réellement implémentées

État : après le lot métier du 14 octobre 2026. Source de vérité : le code (`backend/src/*/*.controller.ts`) et le test d'exhaustivité `backend/test/habilitation/routes-declarees.spec.ts`, qui échoue si une route est ajoutée sans être déclarée ici et dans la matrice.
Les droits viennent de la **matrice RBAC Gate 02A** (`backend/src/habilitation/matrice-officielle.ts`, source : `phase-03-matrice-rbac-delegation.md` fournie par M. Jordan le 16/10/2026). Les droits « D » (délégation) sont **refusés** tant que les délégations (Sprint 2) n'existent pas. Six actions ne figurent pas dans la matrice officielle et portent une hypothèse : voir `HYPOTHESES.md`.

## Règles communes

- **Authentification** : `Authorization: Bearer <jeton d'accès Keycloak>`. Le backend vérifie signature RS256, émetteur, expiration, `typ=Bearer`, `azp=shiku-web`, `sub` (voir `ETAPE-1-AUTHENTIFICATION.md`). Sans jeton valide : **401**.
- **Autorisation** : chaque route déclare `@Public`, `@AuthentifieSeulement` ou `@ExigeDroit('objet.verbe')`. Route non déclarée ou action absente de la matrice : **403** (refus par défaut). Rôle non listé : **403** `Droit insuffisant.`.
- **Compte applicatif** : toute route qui exige un droit exige AUSSI un compte actif dans `utilisateur` lié au `sub` du jeton (**403** `Aucun compte applicatif actif.`). Un jeton valide ne crée aucun compte et n'ouvre rien sans compte (H6 : le rattachement est un acte d'administration).
- **Organisation** : toutes les lectures et écritures sont filtrées par l'organisation du compte. Un objet d'une autre organisation répond **404**.
- **Erreurs** : 400 données invalides `{message:"Données invalides.", erreurs:[{champ,message}]}` (les champs inconnus sont refusés, aucun champ interne ne peut être imposé par le client) ; 404 introuvable ; 409 transition d'état interdite ; 503 base ou Keycloak indisponible.
- **Écritures** : l'action métier et son entrée de journal sont dans UNE transaction (tout ou rien).
- **Pagination** : `limite` (1 à 200, défaut 50 ; 20 côté frontend) et `decalage`.
- **Dates** : ISO 8601 ; les dates saisies exigent un fuseau (`Z` ou `±hh:mm`).

## Périmètre de l'Autorité (DEC-32, provisoire)

Décision (`POST /demandes/:id/decision`) et planification (`POST /audiences`) : 409 si l'agenda n'a aucun rattachement actif (« à rattacher »), 403 si l'Autorité n'y est pas rattachée. Suivi (`demarrer`, `terminer`, `cloturer`) : 409 si l'agenda n'a aucun rattachement actif ; 403 pour une Autorité non rattachée ; l'Assistant agit sur tout agenda rattaché. La consultation reste ouverte.

## États

Demande : `recue → qualifiee → (validee | rejetee | differee) → planifiee → realisee → cloturee` (H14, voir `backend/src/demandes/statuts.ts`). Une décision peut être rendue depuis `recue`, `qualifiee` ou `differee` (H12 : aucune source n'impose la qualification préalable). `differee` accepte ensuite `validee` ou `rejetee`.
Audience : `planifiee → en_cours → terminee → cloturee`.

## Non implémenté (aucune route)

Visiteur (consultation fine, dossier relationnel), catégorie protocolaire (US-05-040), priorité à six critères et son changement (US-05-041/042), reprogrammation, annulation, urgence, arrivée/attente/appel (US-05-053 à 055), salle d'attente, saisie après coup (US-05-062), délégations, conservation et purge, alertes, tableau de bord, verrouillage de session, mobile.
